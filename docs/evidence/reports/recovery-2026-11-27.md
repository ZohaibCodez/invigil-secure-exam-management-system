# Candidate recovery browser verification

**Date:** 2026-11-27  
**Environment:** development preview, fictional candidate/examiner accounts  
**Outcome:** passed the focused journey below  
**Method:** real browser interaction, server reads and selected IndexedDB inspection

The journey used a uniquely named examination, one written question and one
candidate. It did not change another user's examination or grades. The attempt
was not submitted by the test.

## Executed checks

| Step | Observation |
| --- | --- |
| Candidate entry | Instructions appeared before confirmation; timer began after Start |
| Initial notes | Tab A saved `Tab A first`; server version became 1 |
| Blocked send | Only Tab B's answer-save requests were blocked; `Tab B unsent` remained unconfirmed |
| Newer server notes | Tab A saved `Tab A newer`; server version became 2 |
| Reconnection conflict | Tab B displayed its unsent text alongside the current server text; server still held A's version before a choice |
| Explicit replacement | Choosing to keep B's text saved it at version 3 and cleared the conflict |
| Empty-string clear | Clearing notes saved an empty string at version 4; empty notes remained after reload |
| Scratchpad-only recovery | Notes typed with saves blocked were restored after reload and accepted on reconnection at version 5 |
| Device storage failure | Injected `QuotaExceededError` on IndexedDB writes produced a visible storage warning; editing remained possible |
| Server success, device failure | An answer reached the server while the device warning remained; server confirmation was still shown accurately |
| Both paths failing | With server sends blocked and IndexedDB writes failing, the UI did not claim the latest draft was retained locally |
| Retry still failing | Retrying while storage was unavailable kept the warning visible |
| Successful device retry | Restoring writes and retrying cleared the warning only after success; IndexedDB contained the newer answer |
| Successful server retry | Restoring networking saved the newer answer to the server |
| Deadline | The final server deadline exactly matched the initial server deadline |

## Captures observed during the run

The tester returned still images of:

1. The two-copy scratchpad conflict prompt.
2. The device-storage warning after a failed IndexedDB write.
3. Simultaneous server-save and device-storage failure.
4. Successful retry with server confirmation and the warning cleared.

Those images are Replit observation images, not workspace files. Their bytes
were not exposed by the available export tools and are not embedded here.
No continuous video, Playwright trace or HAR file was created by this context.

## Findings and follow-up

The run found a separate sign-in navigation issue: authentication succeeded but
the form could remain mounted in a loading state. It was fixed and checked in
the [focused sign-in follow-up](sign-in-2026-11-27.md).

The scratchpad legend was clarified after the run so its static key could not
be mistaken for the current save status.

## Coverage limits

- The test inspected retained **answer** data after storage recovery; it did not
  separately inspect the scratchpad's device-store copy during injected failure.
- Save timing was observed by polling, not benchmarked.
- This was not a cross-browser/device matrix, crash-recovery certification,
  load test, full PDF acceptance pass or production test.
- A reload warning appeared during one dirty-reload step; it did not prevent
  the observed recovery and was not independently investigated.
